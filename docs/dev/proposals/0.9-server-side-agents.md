# Proposal — Server-side agents (v0.9)

Status: **draft for review**, 2026-09-21. Written after v0.8 landed on
`docs/v0.8-tasks-and-agents` (PR #117) and the orchestrator on
`feat/orchestrator` (PR #118), and before either is released — which is what
makes this a rewrite rather than a migration.

Section numbers below are this document's own. What it would rewrite in
`PROJECT_PLAN.md`: §1, §4.12–§4.17 (substantially), §4.18 (the orchestrator
becomes one instance of the general case), §5.3, §6, §8, §11, §12g (new),
§14.8–9, and CLAUDE.md's hard rules.

---

## 0. The change in one paragraph

v0.8 puts the agent **on the task's host**: sessile writes a bootstrap
there, installs the agent CLI, delivers the user's token in a `.env`, and
tunnels its own tools back over a reverse SSH forward. v0.9 puts the agent
**on the sessile server** and reaches the host the other way round —
through the SSH connection sessile already has. The user authenticates
their agent **once, on the server**, and every task on every host uses it.
The host keeps doing what hosts do: hold the repo, run the build, run the
tests. It just no longer has to hold an agent.

---

## 1. Why

The v0.8 shape was chosen so the agent would be native to the work: its own
shell, its own filesystem, the repo's devcontainer. That is a real
advantage, and it cost more than it was worth:

- **Auth per host.** A token has to reach every host, in a file, for every
  task. Keeping it off disk took the whole `.env`-load-and-delete dance
  (§4.12.9), and the token still sits in a long-lived process environment
  on a machine sessile does not own.
- **An agent CLI on every host,** installed by sessile in user space, kept
  current, duplicated inside every devcontainer, and impossible on hosts
  with no egress to npm — which is most locked-down build boxes.
- **A tunnel to get sessile's own tools back.** The reverse forward, the
  `sessile-mcp` bridge, the embedded arch matrix, the token file, the
  Unix-socket-or-loopback fallback: all of it exists only because the agent
  was on the far side of the connection.
- **Two bootstraps** (`task.sh`, `task.ps1`) that must stay in step, plus a
  third path inside containers.
- **State on someone else's machine.** Resume depends on the host's home
  directory surviving; a rebuilt container or a wiped host loses the
  conversation.

Every one of those is a consequence of the agent's location, not of the
feature. Moving the agent to the server deletes all of them at once.

It also removes a class of bug we have already paid for twice: the only
login and environment failures seen so far came from the one agent that
already runs on the server (the orchestrator), inheriting the server's
environment and home. That is now fixed properly — per-task
`CLAUDE_CONFIG_DIR`/`CODEX_HOME`/`GEMINI_CLI_HOME` and a scrubbed
environment — and the fix is exactly the foundation this proposal builds
on.

**What we give up, stated plainly:** the agent's built-in file and shell
tools no longer see the work. Every read, edit, grep and command becomes a
call over SSH. Whether an off-the-shelf agent works *well* that way is the
one question that cannot be answered from first principles, so §9 starts
with a spike that answers it before anything is deleted.

## 2. Architecture

```
sessile server                                  host
┌─────────────────────────────────────────┐    ┌──────────────────────────┐
│ task  dbg-142-print-crash-3f9a1c        │    │ ~/sessile-tasks/dbg-…/   │
│  ├─ agent session (local PTY)           │    │   repo/        ← the work│
│  │    claude --permission-mode plan     │    │   repos/<name>/          │
│  │    CLAUDE_CONFIG_DIR=.agent/claude   │    │                          │
│  │    MCP over a local Unix socket ─────┼────┼─→ sftp channel (files)   │
│  │                                      │ ssh│   exec channels (run)    │
│  ├─ shell session (the user's pane) ────┼────┼─→ pty channel            │
│  └─ instructions, PROMPT.md, notes/     │    │                          │
└─────────────────────────────────────────┘    └──────────────────────────┘
```

- A task owns **one agent session** on the server and, by default, **one
  shell session** on its host — the split screen (§6). Both are ordinary
  sessions in today's model (`TargetLocal` and `TargetSSH`), sharing the
  task id and group, so the manager, the WS protocol (§5), restart and
  persistence are unchanged.
- The agent's tools are the **same `sessile` MCP server** as v0.8, now
  reached over a Unix socket in the task's own directory on the server. No
  tunnel, no bridge binary, no token in flight.
- Those tools act on the host through **the task's own SSH client**: SFTP
  for files (what `internal/hostops` already does, typed), exec channels
  for commands (what `remoteArch` already does for `uname -m`).

**Connections.** v0.9.0 keeps it simple: the task's tool client dials its
own connection, and the user's shell session dials its own, exactly as SSH
sessions do today. Both are TOFU-checked against the same pinned key, and
neither needs the other to be alive — the agent keeps working after the
user closes the shell pane. Merging them into one connection with several
channels is an optimisation for later, not a prerequisite. Worth knowing
when we do: `sshd`'s `MaxSessions` (10 by default) caps concurrent channels
on one connection, and a long-running build holds one for its whole life.

**Directories.** The agent's state is sessile's own data, so it moves out
of the workspace and into the per-user data dir:

```
<data-dir>/users/<uid>/tasks/<taskID>/
  CLAUDE.md | AGENTS.md | GEMINI.md   # instructions (§4.12.2 as today)
  PROMPT.md                            # the request, if given
  notes/                               # copies of the user's notes
  .agent/{claude,codex,gemini}/        # agent state: settings, history, resume
  .mcp.json, .settings.json            # MCP registration and permission rules
  .sessile.sock, .sessile-token        # the local tool socket
```

The host keeps its task folder — `<tasksDir>/<taskID>/repo` — created over
SFTP, with no bootstrap, no `.env`, no `.tools/`, and nothing sessile has
to install.

## 3. The tool surface

This is the part that decides whether the design is pleasant or miserable,
so it is specified rather than sketched. All of it is scoped to **the
task's own host**, owner-checked exactly like every other lookup.

| Tool | What it does |
|---|---|
| `read_file(path, offset?, limit?)` | File contents, line-numbered, bounded; the shape agents already expect from their own Read |
| `write_file(path, content)` | Create or overwrite |
| `edit_file(path, old, new, replace_all?)` | Exact-string replace — read, substitute, write back |
| `list_dir(path)` | One directory, with types and sizes (`hostops.ListDir`) |
| `glob(pattern, path?)` | File names by pattern — one `rg --files` / `find` on the host |
| `grep(pattern, path?, flags?)` | Content search — `rg` where present, else `grep -r`; bounded output |
| `move/copy/delete(…)` | The typed file operations `hostops` already has |
| `run(command, cwd?, where?, timeout?)` | A command on the host, or inside the task's devcontainer (`where: "container"` → `devcontainer exec`) |

`run` returns exit code plus the tail of combined output (64 KiB, with a
truncation note). Its full output streams to the task panel as it arrives,
so the user watches the build rather than waiting for a verdict. Default
timeout 5 minutes, maximum 60; the user can cancel from the panel.
Background jobs (`run(background: true)` + `job_output`) are deliberately
left to a later version — a timeout plus live output covers the cases we
know.

Alongside these, unchanged from v0.8: the user's **scripts** as tools
(Jira, Jenkins, Artifactory), `set_task_state`, `set_task_summary`,
`task_info`. And for the orchestrator, its own scope (§4.18.1) — which now
differs from a task's only by tool list, not by where it runs.

**Keeping the agent on these tools.** The agent's built-in Read/Edit/Bash
still exist and still point at the server, where there is nothing to do.
Two measures, both needed:

1. The generated instructions say it in the first paragraph: the work is on
   `<host>`, these tools are how you touch it, and the local directory is
   scratch.
2. The generated settings deny the built-in filesystem and shell tools for
   the task's agent (Claude Code `permissions.deny`, codex `--sandbox
   read-only`, gemini's equivalent), so a slip fails loudly instead of
   silently editing the wrong machine.

**Git.** The repo is cloned on the host, so a credential has to reach the
host to clone or push. It reaches it the narrowest way available: the Git
account's credential-helper environment is set **on the exec that needs
it**, never written to disk there, never left in a long-lived process.
That is strictly better than v0.8, where the same values lived in the
agent's own environment for the life of the task.

## 4. Security

This is the real cost of the change and it deserves the bluntest section in
the document.

**The exposure.** An agent on the server runs as sessile's OS user. That
user can read `--data-dir`: every user's `hosts.yml` (SSH passwords and
keys, plaintext by design), `agent.yml` (every user's LLM tokens), and
every script's settings (Jira, Artifactory, Jenkins tokens). An agent is a
program that follows text it reads — a ticket description, a README, a CI
log. One injected instruction in any of them reaches every host of every
user. v0.8 bounded this by construction: the agent ran on the user's own
host, with the user's own credentials, and could reach nothing that was not
already theirs.

**The answer: confine the agent process.** Linux **Landlock** (kernel
5.13+, pure Go, no CGO — already on the plan's Future list for scripts)
applied to the agent before `exec`, inherited by everything it spawns and
impossible to drop:

- read/write: the task's own directory and a temp dir;
- read-only: the agent CLI, its runtime, and the system paths it needs;
- **no access at all** to `--data-dir`, to other users' task directories,
  or to the rest of the filesystem.

The same mechanism applies to **scripts**, which run on the server for
every user today and are documented as equal to shell access there. One
confinement, two problems, and it retires a known Future item.

What Landlock does not do is stop network egress — the agent must reach its
vendor API, so it can also reach anywhere else. Exfiltration by a
prompt-injected agent remains possible; what confinement removes is access
to *other people's secrets* to exfiltrate.

**Where Landlock is unavailable** (older kernel, non-Linux server), the
server refuses to start server-side agents unless the operator passes
`--allow-unconfined-agents`, and says why. Decision needed (§8, O1):
refuse-by-default as written here, or warn-and-continue.

**Kept from v0.8:** TOFU host-key trust, per-user scoping of every lookup,
`--workspace-dir` validation for API-supplied local paths, secret
redaction in tool output, and `allowAgentScripts` as the operator's off
switch. Added: every `run` is logged with its command, host, user and exit
code, and shown live in the task panel — the user sees what their agent did
to their host, not just what it says it did.

## 5. The scope rule this breaks

CLAUDE.md's hard rule says sessile's API never takes a command string, and
that a change drifting toward one should stop. `run` is exactly that, so
the rule gets amended rather than bent — deliberately, in the plan, before
any code:

> An **agent tool** may run a command on **the host of the task it belongs
> to**: one host, never a caller-chosen one, never a list; scoped to the
> authenticated owner of that task; logged with its command and exit code;
> and reachable only through a task's own MCP socket, never as an HTTP
> endpoint. Sessile's **HTTP API** still takes no command string — the
> typed `hostops` operations remain the only file and process surface it
> exposes.

The justification is the trust boundary the plan already uses for SSH
paths (§4.10): the target is the user's own host, reached with the user's
own credentials, in a session they own and can type into themselves. The
agent gains no reach its user did not already have — which is precisely
the sentence that stops being true for the *server*, and is why §4 is not
optional.

## 6. The task page: shell and agent side by side

A task shows two panes: the **host shell** (the user's own terminal, where
they can look around, run things, and interrupt) and the **agent** (its
prompt, its output, its questions). Both are live sessions; both restore on
refresh; both mirror to a second browser exactly as today.

- Desktop: side by side, draggable split, remembered per task.
- Phone: two tabs, agent first — it is what you came for.
- The task panel (state, question, tool activity, approvals) stays as a
  third column or a sheet, as it is now.

The sidebar keeps **one entry per task** with the two sessions under it,
rather than two loose entries. Epics group tasks as they do today.

## 7. What gets deleted

Not a refactor — a subtraction. All of this goes:

- `internal/tasks/templates/task.sh.tmpl`, `agent.sh.tmpl`,
  `task.ps1.tmpl` and their golden files.
- The per-host and per-container agent installers (`installFor`,
  `installForPS`), and `.agent-started`/`.restart-fresh` markers.
- `.env` delivery to hosts, and the load-then-delete dance (§4.12.9).
- The MCP tunnel: `openSSHTunnel`, `sshTools`, `bridgeFiles`,
  `remoteArch`, `goArch`, the embedded `sessile-mcp` binaries, the
  `bridge` make target, `.sessile-port`/`.sessile.sock` on hosts, and
  `cmd/sessile-mcp` itself.
- `SESSILE_IN_CONTAINER`, the `/sessile/...` fixed container paths, the
  `.tools`/`.agent` container mounts.
- The Windows task pipeline, which becomes "a host we run commands on".

What stays: the task spec and its validation, the instructions renderer,
notes, scripts and their approvals, connections and profiles, Git
accounts, devcontainer `up`/`exec` with its fixed mounts and the
docker-socket opt-in, the epic/group model, and the whole session,
protocol and persistence layer.

## 8. Decisions to record, and the v0.8 ones they overturn

| # | Decision | Was (v0.8) |
|---|---|---|
| E1 | **Agents run on the sessile server.** One agent session per task, plus the user's own shell session on the host | D14: one agent session per task, **on the host** |
| E2 | The agent reaches its host through the task's SSH connection: SFTP for files, exec for commands. MCP is local to the server | §5.2: MCP tunnelled to the host over a reverse forward, with a deployed bridge |
| E3 | **One authentication, on the server.** The user's agent token never leaves it | D6 kept tokens-only but delivered them to every host in `.env` |
| E4 | No agent CLI on hosts. It is installed once on the server | D12: install the CLI on the host, and again in every container |
| E5 | `run(command, where: host\|container)` exists as an agent tool, with the bounded rule in §5. The HTTP API still takes no command string | Hard rule: no command strings anywhere |
| E6 | Agent and script processes are confined with Landlock; `--data-dir` is out of reach. Unconfined operation is opt-in | Scripts ran unconfined as sessile's user, documented as shell access; Landlock was Future |
| E7 | A devcontainer is an **execution target** (`devcontainer exec`), not the agent's home. The repo requirement and the fixed mounts stay | D10/D15: the agent lived inside the container, with `/sessile/...` mounts and its own install |
| E8 | Agent state lives on the server, per user and per task, so resume survives host reboots and container rebuilds | Resume depended on the host's home directory |
| E9 | Deleting a task deletes its **server-side** agent directory. The host's task folder is the user's work and is never touched | D5: nothing is ever deleted |
| E10 | The task page is a split screen: host shell + agent | One terminal per task |
| E11 | Windows hosts need no bootstrap; they are hosts we run PowerShell commands on | D7 via a second bootstrap template |
| E12 | Sessile still has **no LLM client** — the agent CLI makes every model call, now from the server | D3, unchanged and worth restating |

Unchanged and load-bearing: TOFU host-key trust, per-user scoping,
workspace validation for API-supplied local paths, one writer goroutine per
WS connection, the §5 wire format, the typed `hostops` surface.

**Open questions for the review:**

- **O1** — Landlock unavailable: refuse server-side agents by default
  (proposed), or warn and continue?
- **O2** — `run` approvals: rely on the agent's own permission mode plus
  sessile's log and live output (proposed), or offer a per-host "confirm
  every command" switch for production hosts?
- **O3** — Deny the agent's built-in shell entirely (proposed), or allow it
  on the server for local scratch work (jq, python) at the cost of
  ambiguity about which machine it is on?
- **O4** — Concurrency: a per-user cap on live agent sessions, and what
  happens when it is reached.
- **O5** — Does the shell session start with every task (proposed), or only
  when the user opens the pane?

## 9. Milestones (to become plan §12g)

**M46 — Spike, throwaway, first.** One task, agent on the server, files and
`run` over SSH against a real repo on a real host. Give it a genuine
change to make — read, edit, build, test, commit — and watch. It decides
the tool names, the instruction wording, and whether the built-in tools
must be denied or merely discouraged. Nothing is deleted until it passes.
*Verify:* the agent completes the change without the user steering it onto
the right tools.

**M47 — The runtime.** Task = server agent session + host shell session.
Per-user task dirs in `--data-dir`, instructions and state there, MCP on a
local socket. Restart resumes; the server survives a host reboot.

**M48 — Files.** `read_file`, `write_file`, `edit_file`, `list_dir`,
`glob`, `grep`, and the typed move/copy/delete, over the task's SFTP
client, with redaction and bounded output.

**M49 — Commands.** `run` with `where: host|container`, live output in the
task panel, timeout, cancel, logging, and the Git credential environment.

**M50 — Confinement.** Landlock for agents and scripts,
`--allow-unconfined-agents`, plan §11 rewritten.

**M51 — The split screen.** Two panes, phone tabs, one sidebar entry per
task with its sessions under it.

**M52 — The subtraction.** Delete §7's list, rewrite §4.12–§4.17, CLAUDE.md
and the README around the new shape.

## 10. Alternatives considered

- **Mount the host's repo on the server (SSHFS/FUSE).** The agent's native
  tools would work unchanged, which is tempting. Rejected: FUSE in the
  server's container, `user_allow_other`, and a grep across a large tree
  over a WAN link is slower than a remote `rg` by a wide margin — the exact
  operation agents do most. Possible later as an opt-in accelerator for
  reads.
- **Clone on the server, sync to the host.** Two working copies, and the
  build still has to happen on the host. Rejected outright.
- **Keep host-side agents as a second mode.** Two pipelines to test and
  document forever, for a case the spike may show is unnecessary.
  Rejected: if someone wants an agent on their host, they can run one —
  sessile's tasks are one way of working, not the only one.
- **A deployed helper binary on the host** (the original phrasing of this
  idea). Rejected once it became clear SFTP and exec channels on the
  existing connection already cover files and commands: a helper would
  reintroduce the arch matrix, the upload, and the version skew that §7
  deletes. If batching or a container-side agent ever needs one, it can
  come back with a reason.

## 11. Risks

- **Agent quality through non-native tools.** The one unknown. M46 exists
  to answer it before anything is deleted.
- **Latency.** Every read and command is a round trip. Fine on a LAN,
  noticeable on a WAN. Mitigated by doing searches host-side in one exec
  rather than reading trees over the wire.
- **SSH throughput.** `x/crypto/ssh`'s fixed 2 MiB window (§11.1) now
  carries file contents and command output as well as keystrokes. Known,
  measured, and deliberately not fixed by swapping the client — but this
  change raises how much it matters.
- **Server load.** One agent process per live task, roughly 0.3–1 GB each.
  A cap and a clear error beat an OOM (O4).
- **Prompt injection.** §4. Confinement is a prerequisite for this design,
  not a nice-to-have.
